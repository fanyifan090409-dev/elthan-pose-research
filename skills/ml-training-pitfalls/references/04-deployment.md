# 04 部署篇：导出 / NCNN / INT8 / 真机基准

格式：**症状 → 根因 → 修法 → 出处**。数据集案例为 pose 训练，规则通用。

## 1. INT8 量化想当然直接上生产

- 症状：INT8 版跑分掉了 4+ 点才回头看。
- 根因：量化前没实测掉点，默认「量化免费」。
- 修法：导出后立刻对拍：INT8 vs FP16 vs PT 同集同口径；掉点超过业务容忍（round5-3 实测掉 4.13 点）就回退 FP32/FP16；判决留档。
- 出处：round5-3 INT8 判决（回退 FP32/FP16）。

## 2. 复杂算子导出失败硬凑

- 症状：导出 pnnx/ncnn 时复杂算子（动态 shape、自定义 op）报错，手改图越改越乱。
- 根因：转换链对复杂算子的支持边界没先摸清。
- 修法：pnnx 切图是唯一正确路线——把大图切成子图逐个转换；导出前先跑最小样例验证算子支持。
- 出处：pose 端侧链 pnnx 切图路线。

## 3. 转换器自身缺陷（Gemm→MatMul、kpt 广播预扩）

- 症状：同一权重 PT 正常、ncnn 输出错位或精度异常，逐层对拍定位到转换器。
- 根因：转换工具缺陷——Gemm 被错误降级为 MatMul、关键点解码的广播形状没预扩。
- 修法：对拍工具逐位对比（PT vs ncnn 同输入）；转换器缺陷先修复工具链再重导出；修复点写进部署报告。
- 出处：YOLO26-pose NCNN 部署链两处缺陷修复。

## 4. 导出链差异无法定位

- 症状：ncnn 输出和 PT 输出有小偏差，不知道哪一环引入。
- 根因：没有逐环节对拍（导出 ONNX → 简化 → pnnx → ncnn 每步都可能改数值）。
- 修法：每环节落中间产物 + 对拍脚本；FP32 冒烟（随机输入逐位对比）作为放行门禁。
- 出处：FP32/FP16 冒烟门禁。

## 5. ncnn 线程/推理标志改了不生效

- 症状：改了 threads/opt 标志想提速，性能纹丝不动。
- 根因：ncnn 的线程数、推理标志只在 `load_param/load_model` 时生效，运行中改无效。
- 修法：标志放在加载阶段设置；改后重新 load 再基准；基准脚本里固化这一点。
- 出处：iOS 真机基准三坑之一。

## 6. 输入名/输入 shape 不匹配

- 症状：推理报错或输出全垃圾，模型文件本身没问题。
- 根因：转换后图改名（如 in0），代码里还用旧输入名/旧 shape。
- 修法：转换后 dump 图信息确认输入名与 shape；代码按转换后图写；输入名做成配置不写死。
- 出处：iOS 真机基准三坑之二（in0 输入名）。

## 7. 真机基准被系统环境干扰

- 症状：基准跑不起来或数据异常（锁屏后 app 被挂起）。
- 根因：移动端系统限制——锁屏拒启动/挂起，后台降频。
- 修法：基准脚本防锁屏（或手动保持亮屏）；报告写清测试条件（机型、系统版本、亮屏状态）。
- 出处：iOS 真机基准三坑之三；iPhone 18 Pro Max 实测 CPU4 89ms / CPU8 90ms / GPU 17.7ms（注意 CPU8 反而比 CPU4 慢——线程切换开销）。

## 8. 部署画布与训练画布不一致

- 症状：训练时 640×640 rect，部署 640×640 非 rect 或其他尺寸，精度行为不一致。
- 根因：量化/剪枝/换骨干都在训练画布上调，没在最终部署画布上复测。
- 修法：任何模型改动（量化、剪枝、结构）都必须在最终部署画布（如 640×640 non-rect）上复测；部署报告记录画布参数。
- 出处：端侧部署验收约定。
