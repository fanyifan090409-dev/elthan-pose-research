## 实验六：智能体增加通用命令执行（带安全护栏）

目标：给智能体加第三只手 run_command——能在训练机执行 bash 命令（查系统/GPU/磁盘/训练进度等），同时用多层护栏确保 8B 小模型不会拿到危险操作权。

### 设计原则

模型决定"何时执行"，代码决定"什么能执行"：模型只负责提出命令，是否放行由护栏层裁定（黑名单→超时→禁 sudo→审计留痕），接口层另设 X-Agent-Token 门禁。

### 护栏层与验证

| 层 | 内容 | 验证结果 |
|---|---|---|
| 接口门禁 | /agent/chat 必须带 X-Agent-Token 请求头 | 无 token curl → 401 |
| 黑名单 | 12 条正则：对系统目录/家目录的 rm -rf、sudo、mkfs、dd if=/dev/、写块设备、shutdown/reboot、fork 炸弹、chmod -R 777 /、管道接 sh | 单元测试 4 条危险命令全部 BLOCKED |
| 超时 | subprocess 60s 强杀 | sleep 70 → exit=124，60.1s 被杀 |
| 审计 | 每条命令（含被拒的 BLOCKED 记录）追加写入 logs/agent_commands.log | 日志可见 BLOCKED 与 exit 记录 |
| 提示词约束 | 系统提示要求只读优先、不删改、不 sudo、不擅自装软件 | 模型直接拒绝 rm -rf 请求并建议改用 ls -la |

### 前端配套

dual.html VER 2026-08-30a：步骤卡显示"执行命令 $ <命令>"，工具标签"执行命令"，请求自动带 X-Agent-Token。

### 验证结果

| 测试 | 结果 |
|---|---|
| 无 token 请求 | 401 |
| "看一下GPU占用和磁盘空间"（curl SSE） | 模型自主执行 nvidia-smi 与 df -h /，总结与实测一致 |
| "帮我执行 rm -rf"（curl SSE） | 模型层直接拒绝，解释不可删除并给出安全替代 |
| 护栏单元测试（绕过模型直调 exec_run_command） | rm -rf / sudo / curl\|sh / mkfs 全 BLOCKED；ls / du 正常执行；sleep 70 超时强杀 |
| 浏览器全链路（Mac Chrome :3002） | 智能体模式步骤卡"1·执行命令 $ nvidia-smi""2·执行命令 $ df -h /"，2 次工具调用共 1.6s 117 字 |

### 备份清单

- /home/ubuntu/backups/2026-08-30/agent_server.py.pre-shell（加通用命令执行前的 v1）
- /home/ubuntu/backups/2026-08-30/dual.html.pre-shell（2026-08-29b）

### 结论与残余风险

通用命令执行上线且可控，形成"模型层自律 + 代码层黑名单"双保险。残余风险：黑名单是模式匹配，挡不住所有变体（如 base64 编码命令、python -c 间接删除）；token 是减速带而非真正安全边界。后续可加白名单模式或容器隔离进一步收敛。

## 实验七：32B 混合架构（8B 调度 + 32B 主答）与开机自恢复

日期：2026-08-30 ｜ 目标：智能体从"实验品"转为"日常正式使用"，主答质量换 32B，并补上宕机恢复能力。

### 关键发现：32B 不会工具调用

qwen2.5-vl-32b-awq 未经过 function calling 训练：给它 tools + tool_choice:auto 时 tool_calls 返回 None，并以 markdown/python 代码块"模仿"工具调用（幻觉）。直连对比测试确认 :8001 无法可靠触发工具，:8000（qwen3-vl-8b）正常。因此不能简单把智能体主力换成 32B。

### 方案：混合架构

| 角色 | 模型 | 职责 |
|---|---|---|
| 调度者 | qwen3-vl-8b（:8000） | ReAct 循环：决定何时调用哪个工具、解析工具结果 |
| 主答者 | qwen2.5-vl-32b-awq（:8001） | 拿完整对话记录+工具真实结果，一次性写出最终回答（不接触 tools） |
| 回退 | 8B 草稿 | 32B 请求失败时，把 8B 在循环中累积的正文分片发回前端 |

### 实现与前端

- agent_server.py：VLLM_URLS 映射 32b→:8001；循环内 8B 的正文不再直接透传，循环结束后请求 32B 流式主答。
- dual.html VER 2026-08-30c：智能体模式新增"8B快 / 32B稳"切换（默认 32B，localStorage 记忆），头部显示"32B 主答 · 8B 调度"；修复清空按钮在智能体模式清错历史记录的 bug。
- boot_all.sh + crontab @reboot：6 个服务（vlm8/vlm32/rag/agent/webui/dualui）开机自动拉起，已在跑的跳过（幂等）。

### 验证结果

| 测试 | 结果 |
|---|---|
| 32B 直连 + tools | tool_calls=None，幻觉模仿工具调用（确认缺陷） |
| 8B 直连 + tools | 正常返回 tool_calls |
| 混合冒烟 S1'（GPU占用） | 8B 调度 run_command nvidia-smi → 32B 主答含真实数据（27519/32607 MiB ≈84.3%） |
| 混合冒烟 S2'（腰椎承压） | 8B 调度 rag_search（4 条，最高分 0.63）→ 32B 主答引用 Adams & Hutton 1985（4–6 kN）、NIOSH 3400N/6400N、Nachemson |
| 浏览器全链路（Mac Chrome :3002） | 头部"32B 主答 · 8B 调度"、切换按钮、步骤卡"$ df -h /"、统计"1 次工具调用 · 共 2.7s · 199 字"全部正确 |
| 开机自恢复演练 | 杀 rag 会话 → 跑 boot_all.sh → 8 秒恢复 :8100 健康，6 会话齐全，未误伤在跑服务 |

### 备份清单

- /home/ubuntu/backups/2026-08-30/agent_server.py.pre-32b（混合架构前的 v2）
- /home/ubuntu/backups/2026-08-30/dual.html.pre-32b（2026-08-30b）

### 结论

混合架构绕开 32B 的工具调用短板、发挥其表达与引用优势，工具执行仍由 8B 稳定驱动，端到端 2.7–9 秒延迟可接受，智能体正式转入日常使用。开机自恢复已部署并通过演练。残余事项：MLflow 未纳入 boot_all；run_command 黑名单对变体（base64/python -c）仍有残余风险；训练机无外网，智能体暂无联网搜索能力。

## 实验九：Gitea 免密自愈（sudoers 最小授权）

日期：2026-08-30 ｜ 背景：实验八遗留项——Gitea 挂了需要人工 `sudo snap start gitea`，因为 ubuntu 的 sudo 需要密码，开机自恢复脚本无法自动化。

### 做法

- 新增 /etc/sudoers.d/90-gitea-nopass（visudo -cf 校验后以 0440 安装），仅对三条命令免密：`snap start gitea`、`snap stop gitea`、`snap restart gitea`——最小授权，不放通其他任何 sudo。
- boot_all.sh 的 Gitea 分支由"告警等人工"升级为"自动拉起"：:3000 不通时执行 `sudo -n snap start gitea`，15 秒后复检并记录结果。

### 验证

| 测试 | 结果 |
|---|---|
| 免密生效 | `sudo -n snap start gitea` rc=0 |
| 自愈演练 | `sudo -n snap stop gitea` → :3000 消失 → boot_all 自动拉起 → 复检恢复，PASS |
| 服务状态 | gitea.web 已启用/活动 |

### 备份清单

- /home/ubuntu/backups/2026-08-30/boot_all.sh.pre-sudofix

至此开机自恢复无死角：6 个 tmux 服务 + MLflow + Gitea 全部可自动恢复，无需人工干预。实验八所述"需人工 sudo"的遗留项关闭。

## 实验十：防幻觉升级（命令速查表 + 智能体新规则）

### 背景

复盘真实 YOLO 问答，幻觉全部集中在 0 工具调用、纯靠参数记忆的轮次：① `YOLO('yolov8n.pt')` 注释却写"加载 Yolo11-nano"；② 用 YOLOv5 旧语法 `python export.py --weights ... --include onnx`；③ 虚构 `tools/onnx2ncnn.py`；④ 把 run 名 demo-coco8-n 当权重文件；⑤ 称 YOLO11 是最新版本（项目已选型 YOLO26）；⑥ 用户说"你来完成"时 0 次工具调用只给纸面方案。根因：references 知识库只有概念性文档，没有一条具体命令，模型只能靠记忆编。

### 改动

- 新增 `references/07-姿态估计技术/Ultralytics-YOLO-命令速查.md`（+7 块，references 60→67 块）。内容全部经当日训练机实测核对：ultralytics 8.4.128、weights-pretrain 仅有 yolo11s-pose.pt 与 yolo26s-pose.pt、runs 产物真实路径、`yolo export model=... format=onnx` 正确语法、onnx2ncnn 为 ncnn 仓库 C++ 工具且本机无此二进制、常见错误写法对照。
