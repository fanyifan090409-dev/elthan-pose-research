# 2026-09-23 学习笔记：引擎选型实验背后的技术点

今天做了件"反潮流"的事：全网都在吹 SGLang，我们用数据说话，最后决定**继续用 vLLM**。这篇笔记把今天碰到的技术点一个个讲透，都是答辩可能被追问的地方。

## 1. 为什么引擎要"选型"，还要先定标准？

换引擎是大事：监控、运维、部署脚本、团队习惯全要跟着动。很多人换引擎的理由是"听说它快"。我们不做这种事。

预注册标准的思路：**先把判定线画好，再跑实验**。今天的线是——SGLang 的多轮 TTFT 要比 vLLM 低 ≥20%，或者聚合吞吐 ≥1.3×，且没有新增故障、单卡显存 ≤32G，才切。为什么是这两个数？TTFT 差 20% 是人能感知的差异线；吞吐 1.3× 是覆盖迁移成本（光今天装 SGLang 就花了 8 轮）的工程线。低于这条线，省下的资源不值得折腾。

这么做的意义：数据出来之后，你没有机会"挑一条对自己有利的线"。评委看到预注册标准，就知道这不是事后圆场。

## 2. TTFT、解码速度、聚合吞吐——三个指标各管什么

- **TTFT（Time To First Token）**：用户说完话到第一个字冒出来的时间。我们产品的反馈要求 <500ms 语音纠错，TTFT 直接决定体验上限。
- **解码速度（tok/s）**：第一个字之后往外吐字的速度。决定一句 30 字的纠正话术要多久说完。
- **聚合吞吐**：一堆人同时请求时，服务器整体产能。决定一张 5090 能服务多少并发用户。

为什么三个都要测？因为单指标会骗人。有的引擎单流飞快但并发一上去就崩（今天没遇到，但这是选型要防的）；有的引擎吞吐高但首字慢，用户体感反而差。A/B/C/D 四组就是把这三角都量一遍。

## 3. 流式测量三个坑（今天最重要的收获，比选型结论更值钱）

**坑 1：`stream=True` 没传，所有 TTFT 都是假的。**

服务器给 LLM 输出用的是 SSE（Server-Sent Events），一句话拆成几百个小包流式发。但 Python requests 如果不传 `stream=True`，它会**把整段响应收完再交给你**——于是你测到的"第一个包的时间"其实是"最后一个包的时间"。首版脚本所有 TTFT 都等于总时长，看起来还挺漂亮。排查了一圈客户端/服务端/代理，最后定位到这一个参数。logs/final_* 就是这批坏数据（ttft_data_s 和 total_s 完全相等），v2_* 才是修好的（TTFT 24ms vs 总时长 700ms）。

教训不是"记得加这个参数"，而是：**先想清楚测量工具在量什么，再信数据**。如果当时没交叉验证就写进日志，今天就拿着假数据去选引擎了。

**坑 2：模型的"思考模式"会让首字时间不稳定。**

Qwen3-VL 在温度 0.7 下有时候会先"思考"再说话——这段时间里 content 字段一直是空的，约 0.8 秒。所以"第一个内容字出现的时间"这个指标会抽风。解法：主指标改成**第一个 SSE 数据包的时间**（不管包里有没有字），内容首字时间只作参考。

**坑 3：缓存冷热不能混着记。**

同一句提示发两次，第二次会被前缀缓存直接命中：16K 输入的 TTFT 从 874ms 掉到 52ms，差 17 倍。如果 5 个样本里混着冷和热，P50 算出来就是垃圾。今天的做法：每组 5 样本，首条是冷值单独记，后 4 条是热值算 P50。

## 4. prefix cache / RadixAttention 是什么

多轮对话每轮都要把历史全量重发一遍。如果每轮都把历史 token 重新算一遍 KV，那对话越长越慢，纯属浪费。

两个引擎都做了"前缀树缓存"：KV cache 按 token 序列组织成一棵前缀树，新请求进来先匹配**最长公共前缀**，只有新增的部分才真正计算。SGLang 管这个叫 RadixAttention，vLLM 叫 prefix cache，原理一样。

今天的直接证据在 sgl_serve_8b.log 里：第 5 轮对话的 prefill 记录是 `#new-token: 1, #cached-token: 3991`——3991 个 token 的 KV 直接白嫖，只算了新加的 1 个。

这为什么对我们产品重要：健身纠错是长对话场景（一组训练 12 次，教练上下文越滚越长）。前缀缓存生效意味着第 12 次纠正的 TTFT 和第 1 次一样快，不随对话变长而变慢。

## 5. CUDA graph 是什么，为什么 prefill 在 multimodal 下被禁用

GPU 上每启动一个 kernel 都有固定开销（CPU 提交任务 → GPU 调度）。一次 token 解码要跑几百个小 kernel，逐个启动的话，启动开销占比很大。

CUDA graph 的思路：把这一串 kernel **提前录制成一张整体图**，之后一次提交整张图执行，省掉几百次启动开销。这招对 decode（形状固定、重复执行）特别好用。

但它要求"录制时和回放时形状一致"。prefill 的输入长度每次不同，而且 Qwen3-VL 是多模态模型（图片的视觉 token 数量随图片变），SGLang 直接拒绝：服务日志原文 "Breakable CUDA graph is incompatible with multimodal model"，把 prefill 的 graph 关了，只保留 decode 的 graph（batch 上限 16）。vLLM 用 piecewise 的方式（按 token 数分桶录制多个图）把这块做得更细，这是它 decode 略快的一部分原因。

## 6. sm_120a 工具链问题本质（今天踩坑最深的地方）

RTX 5090 是 Blackwell 架构，代号 sm_120a。太新了，软件生态还没跟上。

编译链三件套：**nvcc**（编译器前端，把 CUDA 代码编成中间表示 PTX）→ **ptxas**（把 PTX 转成目标 GPU 的机器码），cicc 负责设备端代码编译。三者的版本必须配套。

今天的问题链，每一步都是真实报错：

1. pip 装的 sglang 不带 nvcc（pip 包不打包编译器）；
2. 用系统 CUDA 12.8 的 nvcc：报 "NVCC version must be at least 12.9"——太老；
3. pip 装 nvidia-cuda-nvcc 13.0.88：nvcc 输出 PTX 9.4，但它自带的 ptxas 只认到 9.0，报 "Unsupported .version 9.4"——**自己家的工具不认识自己家的版本**；
4. 升到 13.4.92：又和 cu13 头文件版本对不上（flashinfer 即时编译时报头文件不兼容）；
5. 最终方案：conda 的 cuda-nvcc 13.3 全家桶（nvcc/cicc/ptxas 同一版本）+ 一个软链修复（conda 把库放在 lib/，即时编译却在 lib64/ 找 libcudart.so）。

类比：一套乐高有说明书、积木、成品图三份，但它们是三个批次的——说明书让你拼 A，积木型号对不上，成品图又是 C。conda 全家桶就是买一整套同一批次的。

注意：这些坑不是 SGLang 的错，是 5090 太新。等 flashinfer 修好（缺 curand.h 那个问题），SGLang 可能就一键可装了。所以今天的结论是"备选"而不是"淘汰"——复测触发条件已经写进待办。

## 7. temp=0 为什么输出还不完全一致？

直觉上温度 0 应该完全确定。但今天教练话术组只有 5/8 逐字一致。

原因：GPU 上的浮点加法顺序不确定。FlashAttention 里 tile 怎么切、并行归约的顺序，都受运行时调度影响，同样输入算出的 logit 有极小误差（比如 1e-7 量级）。温度 0 下模型取最大 logit 的 token——如果两个 token 的 logit 本来就很接近，这点误差就足以让模型"翻牌"选另一个 token，然后一路滚雪球。

代码组为什么 8/8 一致？代码任务的概率分布很"尖"（下一个 token 几乎锁定），误差翻不动；话术组有多个都合理的表达，微小的抖动就换了说法。

评委如果问"为什么不用 temp=0 保证可复现"：temp=0 只锁定采样策略，锁不住浮点运算顺序；要完全可复现需要禁用并行归约等手段，会牺牲性能。而且话术场景本来就不需要逐字复现，需要的是"合法且正确"——这正是质量组按"校验通过率"而不是"逐字一致率"来评的原因。

## 8. 答辩可能被问的问题

**Q1：全网都说 SGLang 快，你的数据为什么反着来？**
答：公开基准大多跑在 H100/A100 上。SGLang 的优势很大一部分来自 flashinfer 的深度优化，而 flashinfer 在 5090（sm_120a）上装不起来，我们只能用 triton 注意力后端——它的优化在这台机器上没兑现。基准结论依赖硬件和配置，这正是必须自己测的原因。

**Q2：20% 和 1.3× 的阈值哪来的？**
答：预注册标准。TTFT 低 20% 是体感差异线；1.3× 是覆盖迁移成本的工程线（今天的 8 轮部署手术就是成本的一部分）。低于这个收益不值得动生产实例。

**Q3：剔除 vLLM 冷启动异常算不算挑数据？**
答：不算。剔除规则在结果中显式说明（一次性首轮异常、后两轮复测正常、单流组无对应劣化），原始数据全量保留在 bench_vllm_B.json 可查。透明的异常处理是实验规范的一部分。

**Q4：SGLang 用 triton 后端跑，对它不公平？**
答：我们在 5090 上能跑起来的最优 SGLang 配置就是它。flashinfer 装不上这件事本身就是选型结论的一部分——生产选型比的是"各自最优可达配置"，不是"理论最优配置"。

## 9. 一句话总结

今天做的事本质上是：**用一个可复现的对照流程，把"换引擎"这种看似玄学的决定变成一张可核查的表格**。性能差距全部 <13%，部署成本差距 8 轮——结论自然就出来了。以后任何"XX 是不是更好"的问题，都该走这个流程。
