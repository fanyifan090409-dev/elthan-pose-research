# 2026-09-26 学习笔记：数据、模型容量与部署数值对齐

## 1. 为什么今天能一口气跑三轮？——「单变量对照」的纪律

今天的三轮训练不是随意的三次尝试，而是一张对照表：只允许一个东西变，其他全钉死（同一个 val 集、同样 60 epochs、同样 imgsz 640、同样 seed 42、同样 optimizer=auto）。这样两轮之间的指标差就只能归因于那个变量本身：

- R1→R2：只变「数据量」（15k → 50k）
- R2→R3：只变「模型尺寸」（n → s），顺带把数据补成全量

如果一次同时改数据、改模型、改输入尺寸，指标涨了你也说不清是谁的功劳——就像一次往菜里放三种新调料，好吃也不知道该谢谁。这是实验设计里最朴素也最重要的纪律。

答辩被问「为什么三轮 val 集完全一致？」：COCO 的 train 和 val 文件名本来就不相交，构建脚本从 train 抽样做训练集、val 固定取全部 val，所以三轮天然可比，不是手动挑的。

## 2. 今天最大的认知：数据快饱和了，模型容量才是瓶颈

两个数字摆在一起很有意思：

- 数据 ×3.3（人实例 41k → 137k）→ Pose mAP50-95 +3.4
- 模型 2.87M → 9.4M 参数 → +7.3

为什么数据突然不好使了？关键证据：**全量 COCO 里有效的 person 图只有 53,044 张，50k 抽样已经覆盖了 94%**。也就是说 COCO 这张牌基本打完了——再加数据只是在重复喂几乎相同的信息。这就是「边际收益递减」：模型已经从现有数据里榨不出更多规律，这时候换更大的「容器」（参数更多的模型）才能装下更细的规律。

对项目的意义：下一步真正的增量在**域数据**（竖屏居家健身视频），因为那是 COCO 里完全没有的信息（家里环境、侧面视角、瑜伽垫上的动作），而不是「更多 COCO」。

## 3. mAP50-95 和 OKS 到底是什么（答辩高频题）

- mAP50：IoU（检测框重叠度）阈值固定 0.5 时算的平均精度。框大概对得上就算对，标准很松。
- mAP50-95：阈值从 0.5 到 0.95 每隔 0.05 取一次再平均。要求框越准越好，分数自然更低。
- 关键点的版本用 OKS（Object Keypoint Similarity）替代 IoU：每个关键点按「离真值多远」打分，用高斯函数衰减，不同关键点权重不同（比如眼睛比手肘要求更严）。所以 Pose mAP50-95 = 关键点在各种严格度下的综合平均，比 mAP50 诚实得多。

今天所有汇报都以 mAP50-95 为主指标，因为它更接近真实使用场景里「关键点准不准」的体验。

## 4. 双卡 DDP 是怎么回事

DDP（DistributedDataParallel）流程：每张卡放一份一模一样的模型 → 一个 batch 切成两半各算各的前向/反向 → 两张卡交换梯度并取平均（all-reduce）→ 用平均后的梯度各自更新参数。因为梯度是平均的，两张卡上的模型始终一模一样。

今天 R2/R3：batch 64/卡 × 2 卡 = 有效 batch 128。有效 batch 翻倍时，理论上学习率要按比例放大（linear scaling rule），否则收敛变慢；Ultralytics 的 optimizer=auto 会根据 batch 自动定 lr，所以没手调也能跑。

「双卡结果和单卡会不会不一样？」会有极小的浮点误差（梯度求和顺序不同），量级在 1e-3 以下，对比实验里可忽略。这是答辩可能被追问的点，答得上来说明你真懂 DDP。

## 5. 导出链为什么是 ONNX → PNNX → NCNN？

- ONNX 是「通用中间格式」：PyTorch 先导出 ONNX，任何推理框架都能从 ONNX 起步，这是生态标准动作。
- NCNN 的转换器是 PNNX，它从 PyTorch 的 trace 出发把算子翻译成 NCNN 算子，途中做五轮图优化（今天日志里的 pass_level0~5）。
- 今天实际跑了两条路：ultralytics 内置 ncnn 导出（走 PNNX）出 model.ncnn.param/bin；另用自建的 onnx2ncnn-head 工具出 pose-s 系列变体。
- 变体含义：opt = 图优化后；fp16 = 权重压成半精度（体积减半、端侧更快，可能有极小精度损失）；mm = 另一种输出头形式。它们都要和 PyTorch 原模型做数值对齐，选误差最小的一组上机。

## 6. 数值对齐验证：部署正确性的底线

为什么大费周章比对输出？因为端侧 NCNN 和 PyTorch 哪怕只差 1 个关键点像素，用户就会遇到「姿势明明对却说错」。数值对齐是部署的「出厂质检」。

今天搭的比对链：同一张图 → 同一套 letterbox 预处理 → PyTorch 出「参考答案」（ref）→ NCNN 出「考生答案」（out）→ 逐元素比。

怎么读结果？两个指标配合：

- cos 相似度：两个输出向量的「方向」有多一致。0.9943 说明大体方向对——不是随机乱输出，问题不在整体结构。
- max_abs_diff（最大绝对差）601：说明有位置差得离谱，或整体存在缩放/偏移。

cos 高 + 绝对差大，典型嫌疑是**输出排列顺序 / 缩放系数 / 后处理分支不一致**（比如一个输出的是没过 sigmoid 的原始 logits），而不是权重转错了。下一步就是逐变体比对、定位在哪一层分叉。

补一句 letterbox：把 16:9 原图等比缩放塞进 640×640 正方形输入，空处填灰色 114——检测模型的输入必须是正方形，这是通用预处理，两边必须用同一套，否则比对没有意义。

## 7. 答辩可能被问的问题（自测）

1. 「你的 mAP 和官方 YOLO11s-pose 比怎么样？」→ R3 已到官方 COCO 基线水平（Pose mAP50-95 约 0.50），本项目的创新不在检测器本身，而在域数据微调 + 遮挡补偿打分 + VLM 反馈闭环。
2. 「为什么不用更大的 m 模型一步到位？」→ 端侧 NCNN 部署有算力预算（s 是 21.4 GFLOPs），m 只在云端推理有意义；且今天证明 s 的提升幅度比继续堆数据划算，s 是当前精度/算力甜点。
3. 「三轮实验成本多高？」→ R2 双卡约 1.6 小时、R3 双卡约 2 小时，全部在训练机本地完成，近乎零成本，这也是能一天跑三轮的原因。
4. 「50k 抽样怎么保证无偏？」→ 按 COCO 官方 train 划分用脚本随机抽样（--coco-sample），val 不动，三轮同 val 直接可比。
5. 「训练期间 vLLM 服务怎么办？」→ 看护脚本参数化：训练前停服释放 GPU1，训练结束自动按原配置重建，服务恢复零人工干预——实验与在线服务共存的工程化小闭环。
