# 2026-09-08 学习笔记

今天修了一个「代码就十几行、但特别典型」的 bug：CVAT 骨架连线整体错位。它的价值不在修复本身，而在它背后三个可以讲给评委听的原理。

## 一、这个 bug 到底错在哪：1 起始 vs 0 起始

先看两套数字习惯：

- 数学、教材、日常数数：第 1 个、第 2 个……从 1 开始；
- 计算机数组下标：`[a, b, c]` 里 a 是第 0 个，从 0 开始。

昨天写标签脚本时，17 个关键点按「第 1 个鼻子、第 2 个左眼……」的习惯，把连线端点写成了 1 到 17。但 CVAT 内部把 17 个 sublabel 存在一个 0 起始的数组里（0 到 16）。于是：每条边都连错了目标（该连鼻子的连到了左眼），而且最大端点 17 指向一个**根本不存在的点**。

为什么这种 bug 隐蔽？因为所有数字单独看都是「对的」：17 个点、19 条边，数量没错，错的是**下标基准**。这类错误不会报异常、不会崩程序，只会静默地渲染出错位骨架——比报错可怕得多。

## 二、COCO 17 点骨架：为什么它就够了

COCO 骨架的顺序是固定的：0 鼻子 → 1 左眼 → 2 右眼 → 3 左耳 → 4 右耳 → 5 左肩 → 6 右肩 → 7 左肘 → 8 右肘 → 9 左腕 → 10 右腕 → 11 左髋 → 12 右髋 → 13 左膝 → 14 右膝 → 15 左踝 → 16 右踝。19 条边就是这些点之间的骨骼连接（比如 11-13 是左大腿，13-15 是左小腿）。

深蹲、俯卧撑、硬拉要算什么？髋角（肩-髋-膝）、膝角（髋-膝-踝）、肘角（肩-肘-腕）——全部在 17 点覆盖范围内，一个不多一个不少。

选它的真正理由：**COCO 是姿态估计的事实标准**。YOLO11/26-pose 原生输出的就是 COCO 17 点，我们的标注和模型输出天然对齐，导出即用，不用写转换层。对比方案：MediaPipe 33 点、COCO-WholeBody 133 点——标注成本翻倍以上，模型侧也要跟着改，而三大动作的关节角度计算并不需要手部 21 点那种精度。够用 + 标准 = 最优解。

## 三、为什么用脚本修，而不是打开 GUI 点几下

修复方式本身也值得说：我写了个 Python 脚本，登录 → 读标签 → 重写连线 → 写回 → 复查，全程 REST API。

- **可复现**：脚本重跑一遍等于在任何环境重建修复；
- **可审计**：ISEF 研究日志要求过程记录，GUI 里点三下无迹可寻，脚本就是记录本身；
- **幂等**：跑两次结果一样，不会越修越乱。

还有一个更细的习惯：修复脚本自己打印了复查结果，但我不满足于「脚本说修好了」——又用独立的 curl 命令直接查 API，确认 19 条边、节点 0–16、无 node 17。**修复方自证不算数，独立复核才算数**，这个交叉验证习惯在答辩里是加分项。

## 四、答辩可能被问的问题（自测）

**Q1：你的标注标准是什么？为什么不用更多关键点？**
答：COCO 17 点。三大动作的角度计算（髋/膝/肘角）17 点全覆盖；它是姿态估计事实标准，YOLO26-pose 原生输出同格式，标注与训练零转换成本；更多点（33/133 点）标注成本翻倍而收益不增加。

**Q2：标注数据如果和模型输出格式不一致会怎样？**
答：关键点索引错位会直接毒化训练数据——模型学到的骨骼连接是错的，且这类错误在训练损失里很难暴露，等发现时已经浪费一轮训练。所以索引一致性在标注阶段就要卡死，这也是今天修这个 bug 的原因。

**Q3：骨架连线错位这种 bug，你的流程是怎么兜住的？**
答：三层：一切操作脚本化（可复查）；修复后独立 API 复核（修复方自证不算数）；研究日志留痕（今天的实验日志完整记录了缺陷、修复、验证证据链）。

**Q4：CVAT 的 skeleton 标签机制是怎么回事？**
答：skeleton 标签 = 多个 points 型 sublabel + 一个 svg 模板。svg 里的 data-node-from/to 指向 sublabel 数组下标（0 起始），连线的渲染全靠它。所以「定义关键点」和「定义连接关系」是两件事，后者最容易在下标基准上出错。

## 五、一句话总结

今天的教训一句话：**「数量对」不等于「索引对」**——1 起始和 0 起始之间差的那一位，静默地错位了整副骨架；而脚本化操作 + 独立复核 + 日志留痕，就是把这类静默错误变成可发现、可追溯错误的流程保障。
