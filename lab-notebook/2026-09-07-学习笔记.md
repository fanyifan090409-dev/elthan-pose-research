# 2026-09-07 学习笔记

今天把「数据集建设」的第一块砖铺上了：一条从 B站到 4800 帧标注素材的自动化流水线，和一个能跑起来的 CVAT 标注平台。这两件事背后藏着几个答辩必问的问题，值得掰开讲一遍。

## 一、为什么要先抓网络素材，而不是等试拍集？

先分清两类数据：

- **web-batch1（今天这批）**：从 B站抓的公开教学视频，只用于**内部开发测试**——模型冒烟、角度打分调试、CVAT 标注流程演练、VLM 提示词调试；
- **HomeFit 正式数据集**：将来自己试拍、走合规流程的数据，才是论文的训练数据和实验结果来源。

为什么不能直接等试拍集？因为试拍集要等 9 月的合规表格和 3 人试拍，而开发阶段（标注 SOP、打分引擎、VLM 提示词）现在就需要真实画面来调。用网络素材先跑通全链路，等自拍数据到位后无缝切换，这是「工程验证先行、论文数据后进」的标准打法。

更关键的是合规：视频版权和人物肖像权都归原 UP 主，所以这批数据**永不进训练集、永不公开**。README 里写死了这条红线。ISEF 的合规评审（IRB 类审查）最看重的就是这个——你的数据从哪来、授权是什么、边界画在哪。

## 二、yt-dlp 是怎么工作的？

yt-dlp 是 youtube-dl 的活跃分支，核心概念是 **extractor**：每个网站有一个 extractor 类，负责「从 URL/搜索词解析出真实视频流地址」。`bilisearch10:` 前缀就是 B站搜索接口的 extractor。

看抓取脚本里的格式选择器：

```
bestvideo[height<=720]+bestaudio / bestvideo[height<=720] / best[height<=720] / best
```

翻译成人话：优先选「≤720p 的最优视频流 + 最优音频流合并」；不行就单独视频流；再不行 ≤720p 的单一文件；最后无限制的 best。`--merge-output-format mp4` 让 yt-dlp 调 ffmpeg 把视频音频合成 mp4。

`--download-archive .archive` 是断点续传的关键：每下载成功一个 BV 号就记一行，下次跑自动跳过。所以 .archive 不是垃圾文件，是「已下载清单」，48 行 = 48 个视频的去重记录。

## 三、412 是啥？这跟反爬有什么关系

HTTP 412 本义是 Precondition Failed（请求头里的条件没满足）。但 B站搜索接口返回 412 时，实际含义是**风控拦截**：没有浏览器 Referer 头、请求太密集，服务端直接拒绝。

解法分两步：

1. `--add-headers Referer:https://www.bilibili.com/`——告诉服务器「我是从 B站页面里点的链接」，模拟正常浏览器的来路；
2. `--sleep-requests 5`——每个请求间隔 5 秒，把频率降到人肉点击的水平。

划重点：这是「降低对服务器的打扰」，不是「攻破风控」。学术用途 + 限速 + 仅内部使用，是抓取这件事站得住的底线。工程上还有个更值钱的教训：抓取脚本一定要设计成**可断点续传**——.archive 去重 + retry_missing 按 .info.json 补漏，中断了随时能接着跑，不用从头再来。

## 四、抽帧参数怎么定的：5fps、100 帧、q85

- **5fps**：健身动作帧间变化慢，25/30fps 的相邻两帧几乎一模一样，5fps 信息量没少多少，文件数却少了 5 倍以上；
- **100 帧上限**：5fps × 100 帧 = 视频前 20 秒。教学视频的动作示范多在前段，第一轮够用。局限也诚实记录：如果示范在片中段就会被截掉，后续批次可改成「整片均匀采样」；
- **JPEG q85**：质量/体积的经典平衡点，q85 以上人眼几乎看不出差别，文件却能小一半多。

对比方案：还有「关键帧提取」（只抽 I 帧）——更省，但关键帧位置由编码器决定，不可控；「均匀采样」简单、可控、复现性好，对科研记录更友好。所以选了后者。

## 五、CVAT：为什么选它，它里面长什么样

选型对比：

| 方案 | 优点 | 为什么不选 |
|------|------|------------|
| CVAT | 计算机视觉标注事实标准，骨架标注原生支持，Docker 一键部署，REST API 全流程可脚本化 | 无（选它） |
| Label Studio | 通用 ML 标注，生态活跃 | 强项在文本/NLP 类，骨架标注体验和导出格式不如 CVAT |
| 自建标注 Web | 完全可控 | 开发成本高，还要自己维护，纯属重复造轮子 |

CVAT 的架构（部署后 docker ps 能看到 14 个容器，不是黑盒）：

- **traefik**：入口反代，8080 端口对外；
- **cvat_server**：Django 写的核心 API，所有操作都走它；
- **cvat_db**（PostgreSQL）：标注数据落库；
- **cvat_redis**：缓存 + 任务队列；
- **8 个 worker**：导入、导出、标注、质检、切片、共识、webhook、工具各司其职。为什么拆这么细？因为视频解码、zip 打包这类活很重，拆开才能互不阻塞——你导出 100 个任务的同时，别人还能继续标注。

最后是本项目最看重的一点：**一切都能脚本化**。创建项目、定义骨架标签、上传任务，全是 curl/Python 调的 REST API。GUI 点出来的项目无法复现，脚本可以重跑——ISEF 评审要求过程记录，脚本本身就是记录。

## 六、答辩可能被问的问题（自测）

**Q1：你的训练数据从哪来？版权怎么处理？**
答：两套数据分开。正式训练数据是自拍试拍集（走合规流程）；今天抓的 B站素材是 web-batch1，仅用于内部开发测试，不进训练集、不公开，来源链接全部记录在 manifest.csv，版权与肖像权归原 UP 主。

**Q2：为什么用 COCO 17 点骨架标注？**
答：COCO 17 点是姿态估计的事实标准，YOLO11/26-pose 原生输出就是这个格式，标注直接对齐模型输出，省掉转换层。17 个点覆盖了深蹲/俯卧撑/硬拉的髋、膝、踝、肩、肘全部关节角度计算需求，更多点（如 33 点）标注成本翻倍但收益有限。

**Q3：CVAT 和 Label Studio 怎么选的？**
答：核心需求是骨架标注 + 可脚本化。CVAT 的 skeleton 标签原生支持点、连线、属性，Label Studio 在这块要自己配；而且 CVAT 全流程 REST API 可复现，适合研究日志留痕。

**Q4：抽帧为什么是 5fps 而不是全帧？**
答：健身动作帧间冗余高，5fps 信息损失极小；每视频上限 100 帧控制总量（4800 帧约等于 48 个视频 × 100）。参数依据写在 extract_frames.py 和 README 里，可复现。

**Q5：标注一致性（SOP）怎么保证？**
答：今天建的项目就叫「标注SOP练习」，先用深蹲 60 帧练手，把标注规则写成 SOP；后续多人标注前先过 SOP 练习任务，再正式开标。

## 七、一句话总结

今天的主题是「把开发数据和论文数据分开、把一切操作脚本化」：网络素材解决「马上有数据」，合规红线解决「数据能不能用」，CVAT + REST API 解决「标注能不能复现」。
