## 二、背景与动机

产品路线 W1 要把推理 API 拆分为独立服务。引擎选 vLLM 还是 SGLang 此前无数据依据，为避免跟风，先预注册判定标准再做对照实验：**多轮 TTFT 低 ≥20% 或聚合吞吐 ≥1.3× 才切 SGLang，且无新增故障、单卡显存 ≤32G**。不满足则维持 vLLM。

## 三、实验设计

- 同一权重：`/home/ubuntu/isef/models/qwen3-vl-8b-instruct`，两边均 BF16 高强度（生产同配置），不做量化弱化。
- vLLM：生产实例本身，GPU 1 :8000，`--gpu-memory-utilization 0.85 --max-model-len 16384 --enable-auto-tool-choice --tool-call-parser hermes`，全程零停机。
- SGLang 0.5.20：GPU 0 :8001，`--mem-fraction-static 0.80 --context-length 16384 --attention-backend triton --sampling-backend pytorch --cuda-graph-max-bs-decode 16`，`SGLANG_ENABLE_JIT_DEEPGEMM=0`。
- 基准脚本：`scripts/bench_speed.py`（OpenAI 兼容接口，流式 + include_usage，P50/P95）、`scripts/bench_quality.py`。
- 组设计：
  - A 单流解码：1002 token 提示 × 5 轮，TTFT + 解码速度；
  - B 并发聚合吞吐：并发 1/2/4/8 × 3 轮；
  - C TTFT 三档输入：约 2K/8K/16K token × 5 样本；
  - D 多轮共享前缀：3992 token 前缀 × 5 轮对话 × 2 大轮，对比 SGLang RadixAttention 与 vLLM prefix cache；
  - 质量组：24 条固定提示 temp=0（教练话术 8 + 结构化 JSON 8 + Python 代码 8），校验长度/JSON 合法性/代码语法，跨引擎比对。

| 标准 | 结果 |
|---|---|
| 多轮 TTFT 低 ≥20% | ✗ 不成立：vLLM 反而低约 13%（约 30 ms vs 34 ms） |

## 五、问题与解决

### 1. SGLang 在 RTX 5090（sm_120a）的部署工具链问题（8 轮）

部署成本是本次判定中比性能数字更重的部分。完整链条记录于同日文件 `2026-09-23-模型引擎选型SGLang对比vLLM.md`，日志证据：

- logs/sgl_install.log：pip 安装 sglang 0.5.20 + nvidia-cuda-nvcc-13.4.92 成功；
- logs/conda_nvcc_install.log：最终方案 conda `cuda-nvcc` 13.3.73（nvcc/cicc/ptxas 全家版本一致）装入 env sgl；
- logs/sgl_serve_8b.log：最终启动参数落盘（attention_backend=triton、sampling_backend=pytorch、prefill CUDA graph disabled——服务日志原文 "Breakable CUDA graph is incompatible with multimodal model"）。

问题链：pip 包不带 nvcc → 系统 CUDA 12.8 报 "NVCC version must be at least 12.9" → nvidia-cuda-nvcc 13.0.88 输出 PTX 9.4 而自带 ptxas 只认 9.0（"Unsupported .version 9.4"）→ 升 13.4.92 与 cu13 头文件版本不匹配（flashinfer JIT 报头文件不兼容）→ conda cuda-nvcc 13.3 全家一致 + `lib64/libcudart.so` 软链（conda 包库在 lib/，JIT 却在 lib64 找）→ flashinfer JIT 仍缺 curand.h，注意力换 triton、采样换 pytorch 绕开 → CUDA graph 捕获失败，压到 `--cuda-graph-max-bs-decode 16` + `--mem-fraction-static 0.80`。

### 2. 测量方法学三坑（本轮最重要的方法收获）

1. **requests.post 不带 `stream=True` 会把 SSE 整包缓冲**：首版脚本所有 TTFT 都等于总时长（假象）。logs/final_* 系列即坏数据（如 final_vllm_A.json 中 ttft_data_s=0.861 ≈ total_s=0.862），修复后 v2_* 系列才可信（ttft_data_s=0.024）。排查客户端/服务端/代理后才定位到这一个参数。
2. **Qwen3-VL 在 temp 0.7 下偶发思考模式**（空 content 前缀约 0.8 s），"首字可见时间"不稳定，因此 TTFT 主指标定为**首个 SSE 数据包时间**，content 首字时间作参考。
3. **C 组同提示重复发送会命中 radix/prefix 缓存**，warm TTFT 与冷 prefill 必须分开记录（bench_*_C.json 每组 5 样本中首条为冷值），不可混用。

### 3. 一次性异常的处理

vLLM 并发 8 首轮（4.7 s / 128 tok/s）判定为冷启动异常并剔除。剔除依据：后两轮正常、单流组无对应劣化；剔除规则在结果记录中显式说明，原始数据全量保留可查。
